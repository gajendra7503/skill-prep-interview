Stacks and queues are restricted lists: you may only add and remove at
specific ends. That restriction is the point — it makes the operations O(1)
and makes the *order* of processing explicit. Stacks model "most recent
first" (undo, function calls, nested brackets); queues model "first come,
first served" (print jobs, task workers, BFS).

```text
STACK (LIFO)                 QUEUE (FIFO)
   push / pop                enqueue ->  [ c | b | a ]  -> dequeue
      |  ^                               back        front
      v  |
   [ c ]  <- top
   [ b ]
   [ a ]
```

For a stack, a JavaScript array is enough: `push`, `pop` and `at(-1)` are
all O(1). Note that `[].pop()` returns `undefined` rather than throwing.

## Problem: balanced brackets

Is `"{[()()]}"` correctly nested? Each closing bracket must match the
**most recent unmatched** opening bracket — "most recent" is the signal for a
stack.

```js
function isValid(s) {
  const pairs = { ")": "(", "]": "[", "}": "{" };
  const stack = [];
  for (const ch of s) {
    if (ch === "(" || ch === "[" || ch === "{") stack.push(ch);
    else if (ch in pairs) {
      if (stack.pop() !== pairs[ch]) return false; // wrong type, or nothing open
    }
  }
  return stack.length === 0; // anything left open is unbalanced
}
console.log(isValid("{[()()]}"), isValid("([)]"), isValid("(("), isValid("))"), isValid(""));
// true false false false true
```

Time O(n), space O(n). The two classic misses are `"(("` (forgetting the
final emptiness check) and `"))"` (popping an empty stack). Popping an empty
array gives `undefined`, which never matches, so this version handles it.

## Problem: a stack with O(1) minimum

Design a stack supporting `push`, `pop`, `top` and `min`, all in O(1).
Scanning for the minimum is O(n). The trick: keep a second stack where each
entry is "the minimum of everything at or below this level".

```js
class MinStack {
  #items = [];
  #mins = [];
  push(x) {
    this.#items.push(x);
    const m = this.#mins.length ? Math.min(x, this.#mins.at(-1)) : x;
    this.#mins.push(m);
  }
  pop() { this.#mins.pop(); return this.#items.pop(); }
  top() { return this.#items.at(-1); }
  min() { return this.#mins.at(-1); }
}
const ms = new MinStack();
ms.push(5); ms.push(3); ms.push(7); ms.push(3);
console.log(ms.min());          // 3
ms.pop(); console.log(ms.min()); // 3  (the earlier 3 is still there)
ms.pop(); ms.pop();
console.log(ms.min(), ms.top()); // 5 5
```

O(1) per operation, O(n) extra space. Interviewers often probe the duplicate
case (two 3s) — this design handles it because every push records a minimum.
A related family, "next greater element", uses a *monotonic* stack — see
"Designing Data Structures: LRU/LFU Caches, Monotonic Stacks & Rate
Limiters".

## Queues: why not just use shift?

`arr.push` plus `arr.shift` *works* as a queue, but `shift` moves every
remaining element, so it is O(n) in general. Draining a queue of n items
becomes O(n²). Measured on Node 24 (your numbers will differ):

```text
items     push/shift     head-index Queue (below)
20,000       782 ms            12 ms
40,000     1,229 ms             7 ms
80,000     5,461 ms            33 ms
```

The fix: never move elements. Keep a `head` index that advances on
dequeue, and compact the array occasionally so memory does not grow forever.

```js
class Queue {
  #items = [];
  #head = 0;
  enqueue(x) { this.#items.push(x); }
  dequeue() {
    if (this.#head === this.#items.length) return undefined;
    const x = this.#items[this.#head];
    this.#items[this.#head++] = undefined;          // release the reference
    if (this.#head > 1024 && this.#head * 2 > this.#items.length) {
      this.#items = this.#items.slice(this.#head);  // occasional compaction
      this.#head = 0;
    }
    return x;
  }
  peek() { return this.#items[this.#head]; }
  get size() { return this.#items.length - this.#head; }
}
const q = new Queue();
q.enqueue("token-101"); q.enqueue("token-102"); q.enqueue("token-103");
console.log(q.dequeue(), q.peek(), q.size); // token-101 token-102 2
```

Compaction copies at most the live half and happens only after at least as
many dequeues, so dequeue stays amortised O(1). A linked list with head and
tail pointers (see "Linked Lists") is the other standard O(1) queue.

## Problem: queue using two stacks

A favourite design question. Push into an `in` stack; to dequeue, pop from
an `out` stack, refilling it from `in` only when it is empty. Refilling
reverses the order, turning LIFO into FIFO.

```js
class TwoStackQueue {
  #in = [];
  #out = [];
  enqueue(x) { this.#in.push(x); }
  dequeue() {
    if (this.#out.length === 0)
      while (this.#in.length) this.#out.push(this.#in.pop());
    return this.#out.pop();
  }
}
const tq = new TwoStackQueue();
tq.enqueue(1); tq.enqueue(2); tq.enqueue(3);
console.log(tq.dequeue());                       // 1
tq.enqueue(4);
console.log(tq.dequeue(), tq.dequeue(), tq.dequeue(), tq.dequeue()); // 2 3 4 undefined
```

A single dequeue can be O(n), but each element moves from `in` to `out`
exactly once, so the cost is **amortised O(1)**. Refilling `out` when it
still has items is the bug interviewers look for — it breaks FIFO order.

## Fixed capacity: the ring buffer

When the maximum size is known (say, the last 1,000 UPI events for a
dashboard), a **circular buffer** uses a fixed array plus `head` and `size`.
The back slot is `(head + size) % capacity`, and dequeuing just advances
`head = (head + 1) % capacity` — indices wrap around and nothing is ever
reallocated or moved.

```text
capacity 3: push a, b, c -> [ a | b | c ] head=0
dequeue (a)              -> [ a | b | c ] head=1   (slot 0 is now free)
push d                   -> [ d | b | c ] head=1   (wrapped into slot 0)
```

Allowing adds and removes at both ends turns it into a **deque**
(double-ended queue), which sliding-window maximum problems rely on. Queues
also drive breadth-first search in "Graphs: Representation, BFS & DFS"; when
items need ordering by priority instead of arrival, use "Heaps & Priority
Queues".
