"Design a data structure that supports X and Y in `O(1)`" is a favourite
senior interview format. There is rarely a new algorithm involved; the
skill is **composing** simple structures so that each one covers the other's
weakness. A hash map gives `O(1)` lookup but no order; a linked list gives
`O(1)` reordering but no lookup. Together they make an LRU cache.

## LRU cache

Keep at most `capacity` entries; on overflow, evict the **least recently
used** one. Both `get` and `put` must be `O(1)`.

```text
map: key -> node            most recent                  least recent
                     head <-> [PNR3] <-> [PNR1] <-> ... <-> tail
get(k): find node via map, unlink it, move to front        O(1)
put(k): insert at front; if over capacity, drop tail.prev  O(1)
```

### The JavaScript shortcut

A JavaScript `Map` iterates in **insertion order**, so deleting and
re-inserting a key moves it to the "newest" end, and `map.keys().next()`
gives the oldest:

```js
class LRUCache {
  constructor(capacity) { this.capacity = capacity; this.map = new Map(); }
  get(key) {
    if (!this.map.has(key)) return -1;
    const value = this.map.get(key);
    this.map.delete(key); this.map.set(key, value); // move to most-recent end
    return value;
  }
  put(key, value) {
    if (this.map.has(key)) this.map.delete(key);
    else if (this.map.size === this.capacity) this.map.delete(this.map.keys().next().value); // oldest
    this.map.set(key, value);
  }
}
const lru = new LRUCache(2);
lru.put("PNR1", "Confirmed"); lru.put("PNR2", "RAC");
console.log(lru.get("PNR1"));                       // Confirmed
lru.put("PNR3", "WL 12");                           // evicts PNR2
console.log(lru.get("PNR2"), [...lru.map.keys()]);  // -1 [ 'PNR1', 'PNR3' ]
```

Mention this in an interview, but expect the follow-up: "Now do it without
relying on `Map` ordering." That is the doubly linked list version, with
sentinel `head` and `tail` nodes so there are no null checks:

```js
class Node { constructor(k, v) { this.key = k; this.val = v; this.prev = this.next = null; } }
class LRUList {
  constructor(capacity) {
    this.capacity = capacity; this.map = new Map();
    this.head = new Node(); this.tail = new Node();
    this.head.next = this.tail; this.tail.prev = this.head;
  }
  #unlink(n) { n.prev.next = n.next; n.next.prev = n.prev; }
  #pushFront(n) { n.next = this.head.next; n.prev = this.head; this.head.next.prev = n; this.head.next = n; }
  get(key) {
    const n = this.map.get(key);
    if (!n) return -1;
    this.#unlink(n); this.#pushFront(n);
    return n.val;
  }
  put(key, val) {
    let n = this.map.get(key);
    if (n) { n.val = val; this.#unlink(n); this.#pushFront(n); return; }
    if (this.map.size === this.capacity) {
      const old = this.tail.prev; this.#unlink(old); this.map.delete(old.key); // node stores its key for this
    }
    n = new Node(key, val); this.map.set(key, n); this.#pushFront(n);
  }
}
const l2 = new LRUList(2);
l2.put(1, "a"); l2.put(2, "b"); l2.get(1); l2.put(3, "c"); // evicts 2
console.log(l2.get(2), l2.get(1), l2.get(3)); // -1 a c
```

## LFU cache

Evict the **least frequently used** key; break ties by least recently used.
The `O(1)` design keeps a bucket of keys per frequency plus `minFreq`:

```text
vals: key -> value      freq: key -> count
buckets: 1 -> {c}   2 -> {}   3 -> {a}        minFreq = 1
```

Each bucket is a `Set`, which also iterates in insertion order, giving LRU
within the same frequency.

```js
class LFUCache {
  constructor(capacity) {
    this.capacity = capacity; this.vals = new Map(); this.freq = new Map();
    this.buckets = new Map(); this.minFreq = 0;
  }
  #touch(key) {
    const f = this.freq.get(key);
    this.buckets.get(f).delete(key);
    if (this.buckets.get(f).size === 0) { this.buckets.delete(f); if (this.minFreq === f) this.minFreq = f + 1; }
    this.freq.set(key, f + 1);
    if (!this.buckets.has(f + 1)) this.buckets.set(f + 1, new Set());
    this.buckets.get(f + 1).add(key);
  }
  get(key) {
    if (!this.vals.has(key)) return -1;
    this.#touch(key);
    return this.vals.get(key);
  }
  put(key, value) {
    if (this.capacity === 0) return;
    if (this.vals.has(key)) { this.vals.set(key, value); this.#touch(key); return; }
    if (this.vals.size === this.capacity) {
      const bucket = this.buckets.get(this.minFreq);
      const evict = bucket.values().next().value;
      bucket.delete(evict); if (bucket.size === 0) this.buckets.delete(this.minFreq);
      this.vals.delete(evict); this.freq.delete(evict);
    }
    this.vals.set(key, value); this.freq.set(key, 1);
    if (!this.buckets.has(1)) this.buckets.set(1, new Set());
    this.buckets.get(1).add(key);
    this.minFreq = 1; // a brand-new key always has the lowest frequency
  }
}
const lfu = new LFUCache(2);
lfu.put("a", 1); lfu.put("b", 2); lfu.get("a"); lfu.put("c", 3); // evicts b (freq 1)
console.log(lfu.get("b"), lfu.get("a"), lfu.get("c"));           // -1 1 3
lfu.put("d", 4);                                                 // a=3, c=2: evicts c
console.log(lfu.get("c"), lfu.get("a"), lfu.get("d"));           // -1 1 4
```

The subtle line is `minFreq = f + 1` inside `#touch`: it is only safe
because the touched key moves to exactly `f + 1`.

## Monotonic stacks

A **monotonic stack** keeps elements in increasing or decreasing order,
popping anything that breaks the order. Each element is pushed and popped
once, so a whole pass is `O(n)` even with the inner `while`.

**Next greater element**: for each index, the first later value that is
larger. Keep a stack of indices still "waiting" for an answer; when a
bigger value arrives, it answers everyone smaller on top of the stack.

```js
function nextGreater(nums) {
  const res = new Array(nums.length).fill(-1);
  const stack = []; // indices, values decreasing from bottom to top
  for (let i = 0; i < nums.length; i++) {
    while (stack.length && nums[stack.at(-1)] < nums[i]) res[stack.pop()] = nums[i];
    stack.push(i);
  }
  return res;
}
console.log(nextGreater([2, 1, 2, 4, 3])); // [ 4, 2, 4, -1, -1 ]
```

Store `i - j` instead of the value and you have "days until a warmer
temperature". The same pattern solves stock span, largest rectangle in a
histogram and trapping rain water. Interviewers often ask you to justify the
`O(n)` bound — the push-once, pop-once argument is the answer.

## Rate limiters

An API gateway allows each client `N` requests per time window.

| Algorithm | Idea | Memory per client | Trade-off |
|---|---|---|---|
| Fixed window counter | count per clock minute | `O(1)` | bursts of 2N at window edges |
| Sliding window log | store each timestamp, drop old ones | `O(N)` | exact, more memory |
| Token bucket | tokens refill at rate `r`, each request spends one | `O(1)` | allows controlled bursts |

```js
class TokenBucket {
  constructor(capacity, refillPerSec, now = Date.now) {
    this.capacity = capacity; this.rate = refillPerSec; this.now = now;
    this.tokens = capacity; this.last = now();
  }
  allow() {
    const t = this.now();
    this.tokens = Math.min(this.capacity, this.tokens + ((t - this.last) / 1000) * this.rate);
    this.last = t;
    if (this.tokens >= 1) { this.tokens -= 1; return true; }
    return false;
  }
}
let clock = 0;                                   // injectable clock makes it testable
const tb = new TokenBucket(3, 1, () => clock);
const r = [];
for (let i = 0; i < 5; i++) r.push(tb.allow());   // burst of 5 at t = 0
clock = 2000; r.push(tb.allow(), tb.allow(), tb.allow()); // 2 tokens refilled
console.log(r.join(" ")); // true true true false false true true false
```

Refilling lazily on each call means no timers and `O(1)` per request. In a
distributed system the state lives in a shared store such as Redis, and the
read-modify-write must be atomic.

## Common mistakes

- In the linked-list LRU, forgetting to store the key in the node, so you
  cannot delete the evicted entry from the map.
- Updating an existing key in `put` without counting it as a "use".
- In LFU, not resetting `minFreq` to 1 on insert.
- Rate limiters that call `Date.now()` directly — impossible to unit test.
