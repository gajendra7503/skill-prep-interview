Some logic needs to run **before** any route in your app renders — checking
whether a visitor is signed in, redirecting based on locale, or rewriting a
request to a different path. Next.js runs a single function for every
matching request, ahead of routing, for exactly this purpose.

## The `proxy` file convention

As of Next.js 16, this function lives in `proxy.ts` at the project root (or
inside `src/`), exported as `proxy`. This app's own `src/proxy.ts` is a real
example — it refreshes the signed-in user's Supabase session on every
request so Server Components downstream always see a valid session:

```ts
// src/proxy.ts
import { type NextRequest } from "next/server";
import { updateSession } from "@/lib/supabase/middleware";

export async function proxy(request: NextRequest) {
  return await updateSession(request);
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)"],
};
```

> Older Next.js projects (and most tutorials/blog posts today) still use the
> `middleware.ts` file with an exported `middleware` function — same idea,
> older name. If you see both a `middleware.ts` and a `proxy.ts` file in a
> project, Next.js will error and tell you to keep only `proxy.ts`.

## The `matcher`: scoping which requests run through it

Without a `matcher`, the function runs on **every** request, including
static assets — usually wasteful. The `config.matcher` array is a set of
path patterns (or a regex, as above) that limits it to the routes that
actually need it.

## Redirecting unauthenticated visitors

A common use case: protect a section of the site by checking for a session
cookie before the route ever renders, and redirect if it's missing.

```ts
// src/proxy.ts
import { NextResponse, type NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  const isLoggedIn = request.cookies.has("session");
  const isProtectedRoute = request.nextUrl.pathname.startsWith("/dashboard");

  if (isProtectedRoute && !isLoggedIn) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/dashboard/:path*"],
};
```

This runs before routing, ahead of any Server Component code — cheaper
than letting the page start rendering and only then discovering the user
isn't authorized.

## What it can't do

In Next.js 16 the proxy runs on the **Node.js runtime** (the old Edge-only
restriction of middleware is gone), and the `runtime` segment option is not
allowed in `proxy.ts` — setting it throws an error. It still runs on *every*
matched request, though, so keep it fast: reading cookies, redirecting and
rewriting are a good fit, while database queries and heavy work belong in
the page, a Route Handler or a Server Action. Proxy is also not a complete
authorization layer on its own — re-check permissions where data is read.

### Try it yourself

Add a `matcher` that also protects `/courses/*` routes, and extend the
redirect to preserve the originally requested path as a `?next=` query param
so the login page can send the user back after signing in.
