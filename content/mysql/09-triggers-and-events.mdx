Triggers run SQL automatically when rows change; events run SQL on a
schedule. Both are easy to write and easy to misuse, so interview questions
tend to focus on the rules (`NEW` vs `OLD`, what does *not* fire a trigger)
and on whether you know when to avoid them.

## Trigger basics

A MySQL trigger is attached to one table and fires `BEFORE` or `AFTER` an
`INSERT`, `UPDATE` or `DELETE`. MySQL supports only **row-level** triggers
(`FOR EACH ROW`); there are no statement-level triggers, so an `UPDATE`
touching 10,000 rows runs the trigger body 10,000 times.

Inside the body, `NEW` is the incoming row and `OLD` is the existing row:

| Event | `OLD` | `NEW` |
| --- | --- | --- |
| INSERT | not available | the row being inserted |
| UPDATE | row before the change | row after the change |
| DELETE | the row being deleted | not available |

`NEW` can be modified only in a `BEFORE` trigger (`SET NEW.col = ...`),
which makes `BEFORE` the place for normalising or validating data. `AFTER`
triggers see final values and are used for side effects such as auditing.

```sql
DELIMITER //
CREATE TRIGGER orders_before_insert
BEFORE INSERT ON orders
FOR EACH ROW
BEGIN
  IF NEW.amount <= 0 THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Order amount must be positive';
  END IF;
  SET NEW.created_at = COALESCE(NEW.created_at, NOW());
END //
DELIMITER ;
```

`SIGNAL` aborts the statement with an error. Today a `CHECK` constraint
(enforced since MySQL 8.0.16) is the simpler way to express the amount rule.

## Example: an audit log

A common interview design question is "track every salary change".

```sql
CREATE TABLE salary_audit (
  audit_id    BIGINT AUTO_INCREMENT PRIMARY KEY,
  emp_id      INT NOT NULL,
  old_salary  DECIMAL(12,2),
  new_salary  DECIMAL(12,2),
  changed_by  VARCHAR(100),
  changed_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

DELIMITER //
CREATE TRIGGER employees_after_update
AFTER UPDATE ON employees
FOR EACH ROW
BEGIN
  IF NOT (OLD.salary <=> NEW.salary) THEN
    INSERT INTO salary_audit (emp_id, old_salary, new_salary, changed_by)
    VALUES (OLD.emp_id, OLD.salary, NEW.salary, CURRENT_USER());
  END IF;
END //
DELIMITER ;

UPDATE employees SET salary = 275000 WHERE emp_id = 2;
SELECT emp_id, old_salary, new_salary FROM salary_audit;
-- emp_id | old_salary | new_salary
--      2 |  250000.00 |  275000.00
```

The null-safe `<=>` comparison avoids logging rows whose salary did not
actually change, including `NULL` to `NULL`. On InnoDB the trigger runs in
the **same transaction** as the triggering statement: if the audit insert
fails, the `UPDATE` fails too, and a rollback removes both.

## Pitfalls interviewers ask about

- **Hidden logic.** Developers reading application code cannot see that an
  `UPDATE` also writes elsewhere; debugging "mystery rows" is painful.
- **Row-by-row cost.** Bulk updates multiply the trigger's work and lock
  footprint; a heavy trigger can turn a fast batch into a slow one.
- **Cannot modify the same table.** A trigger on `orders` cannot `UPDATE`
  `orders` (error 1442); use `SET NEW.col` in a `BEFORE` trigger instead.
- **Not everything fires them.** Foreign-key cascades (`ON DELETE CASCADE`)
  do **not** fire triggers on the child table, and `TRUNCATE` and
  `DROP TABLE` fire no delete triggers. `REPLACE` may fire delete and insert
  triggers; `INSERT ... ON DUPLICATE KEY UPDATE` fires the insert trigger,
  then the update triggers if a duplicate is found.
- **Ordering.** Several triggers with the same timing and event are allowed;
  control their order with `FOLLOWS` or `PRECEDES`.

Inspect existing triggers with `SHOW TRIGGERS` or
`information_schema.TRIGGERS`.

## The Event Scheduler

Events are scheduled SQL jobs run by the server itself, a built-in cron.
The scheduler thread is controlled by `event_scheduler`, which is `ON` by
default in MySQL 8.0.

```sql
SHOW VARIABLES LIKE 'event_scheduler';   -- ON

CREATE EVENT purge_old_sessions
ON SCHEDULE EVERY 1 DAY
STARTS '2026-01-01 02:00:00'
DO
  DELETE FROM sessions WHERE last_seen < NOW() - INTERVAL 30 DAY;

CREATE EVENT one_time_cleanup
ON SCHEDULE AT CURRENT_TIMESTAMP + INTERVAL 1 HOUR
DO
  DELETE FROM carts WHERE status = 'abandoned';
```

A one-time `AT` event is dropped after it runs unless declared
`ON COMPLETION PRESERVE`. Events can be paused with
`ALTER EVENT ... DISABLE`. Typical uses are purging old data and refreshing
summary tables. Caveats: failures only show in the error log, there is no
retry or alerting, and events replicated to a replica are created disabled
there. Many teams therefore prefer an external scheduler for critical jobs.

### Try it yourself

Add an `order_audit` table and an `AFTER DELETE` trigger on `orders` that
copies the deleted row into it. Delete an order, check the audit table, then
roll back inside a transaction and confirm both changes disappear. Finally,
write an event that rebuilds a `daily_revenue` summary table every night at
01:00.
