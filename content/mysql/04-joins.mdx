Joins are the heart of relational querying and the single most common
topic in SQL interviews. Beyond "draw the Venn diagram", expect questions
on finding rows with **no** match, on why a `LEFT JOIN` quietly turned into
an inner join, and on how to do a full outer join in MySQL, which has no
`FULL OUTER JOIN` keyword.

Sample data used below:

| customers.id | name | city |
| --- | --- | --- |
| 1 | Asha | Pune |
| 2 | Ravi | Delhi |
| 3 | Meera | Chennai |

| orders.id | customer_id | total |
| --- | --- | --- |
| 101 | 1 | 2499.00 |
| 102 | 1 | 649.00 |
| 103 | 2 | 1999.00 |
| 104 | 9 | 399.00 |

Order 104 points at a customer that does not exist (imagine the foreign key
was missing), and Meera has no orders.

## INNER JOIN

Returns only rows that match on both sides:

```sql
SELECT c.name, o.id, o.total
FROM customers c
INNER JOIN orders o ON o.customer_id = c.id;
-- Asha 101 2499.00 | Asha 102 649.00 | Ravi 103 1999.00
```

In MySQL, `JOIN`, `INNER JOIN` and `CROSS JOIN` are syntactic equivalents;
what matters is whether you supply a join condition.

## LEFT and RIGHT JOIN

A `LEFT JOIN` keeps **every** row from the left table; where nothing
matches, the right side's columns are `NULL`.

```sql
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;
-- Asha 101 | Asha 102 | Ravi 103 | Meera NULL
```

`RIGHT JOIN` is the mirror image (keeps all `orders`, so 104 appears with a
NULL name). Most teams write only `LEFT JOIN` and swap table order, which
is easier to read.

## CROSS JOIN

A Cartesian product: every left row paired with every right row (3 x 4 = 12
rows here). Useful for generating combinations, e.g. every product for
every city in a price grid. An accidental cross join — a forgotten `ON` —
is a classic cause of exploding row counts.

## Self join

Join a table to itself with two aliases. If `customers` has a nullable
`referred_by` column pointing at another customer:

```sql
SELECT c.name AS customer, r.name AS referred_by
FROM customers c
LEFT JOIN customers r ON r.id = c.referred_by;
```

The same pattern answers "employees who earn more than their manager".

## Anti-joins: rows with no match

"Customers who have never ordered" has three common forms:

```sql
-- 1. LEFT JOIN ... IS NULL
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- 2. NOT EXISTS
SELECT c.* FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- 3. NOT IN
SELECT c.* FROM customers c
WHERE c.id NOT IN (SELECT customer_id FROM orders);
```

All three return Meera here. But `NOT IN` breaks if the subquery returns a
`NULL`. Suppose an order has `customer_id = NULL`:

```sql
SELECT * FROM customers WHERE id NOT IN (1, 2, NULL);
-- Empty set
```

`3 NOT IN (1, 2, NULL)` means `3 <> 1 AND 3 <> 2 AND 3 <> NULL`, and the
last term is `UNKNOWN`, so the whole condition is never true. **Prefer
`NOT EXISTS`**: it is NULL-safe, clearly expresses intent, and since MySQL
8.0.17 the optimizer converts both `NOT EXISTS` and `NOT IN` subqueries
into an internal antijoin. In the `LEFT JOIN` form, test a column that
cannot be NULL in a real match, such as the primary key.

## Emulating FULL OUTER JOIN

MySQL does not support `FULL OUTER JOIN`. Combine a left join with the
unmatched rows of a right join:

```sql
SELECT c.id AS cust_id, c.name, o.id AS order_id
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
UNION ALL
SELECT c.id, c.name, o.id
FROM customers c RIGHT JOIN orders o ON o.customer_id = c.id
WHERE c.id IS NULL;
```

| cust_id | name | order_id |
| --- | --- | --- |
| 1 | Asha | 101 |
| 1 | Asha | 102 |
| 2 | Ravi | 103 |
| 3 | Meera | NULL |
| NULL | NULL | 104 |

Using `UNION` without the `WHERE c.id IS NULL` filter also works, but it
dedupes by sorting or hashing and would wrongly collapse rows that are
genuinely identical. `UNION ALL` plus the filter is exact and cheaper.

## ON vs WHERE in outer joins

For an inner join, a condition behaves the same in `ON` or `WHERE`. For an
outer join it does not:

```sql
-- Filter in WHERE: Meera disappears (her o.total is NULL)
SELECT c.name, o.id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.total > 1000;
-- Asha 101 | Ravi 103

-- Filter in ON: all customers kept, only big orders attached
SELECT c.name, o.id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.total > 1000;
-- Asha 101 | Ravi 103 | Meera NULL
```

`ON` decides which right rows _match_; `WHERE` filters the joined result
afterwards. A `WHERE` condition on the right table that rejects NULLs turns
the `LEFT JOIN` into an inner join, and MySQL's optimizer will rewrite it
as one.

### Try it yourself

Using `products` and `order_items`, list every product with the number of
units sold in March 2025, showing 0 for products that sold nothing. Then
list products never sold at all using `NOT EXISTS`, and explain what goes
wrong if you put the March date filter in `WHERE` instead of `ON`.
