A JSON Web Token (JWT) is a signed, self-contained credential. Instead of
looking up a session in a store, the server verifies the token's signature
and trusts the claims inside. That makes JWTs popular for APIs used by mobile
apps and other services — but it also brings trade-offs interviewers love to
probe.

## Anatomy of a JWT

A JWT is three base64url-encoded parts joined by dots:
`header.payload.signature`.

```json
// header
{ "alg": "HS256", "typ": "JWT" }

// payload (the "claims")
{ "sub": "42", "role": "admin", "iat": 1760400000, "exp": 1760400900 }
```

The signature is computed over the header and payload with a secret (HS256)
or a private key (RS256, ES256). Anyone can **decode** the payload — it is
encoded, not encrypted — so never put passwords, card numbers or other
secrets in it. Keep claims minimal: a user ID (`sub`), a role, and expiry.

## Signing and verifying with jsonwebtoken

```js
import jwt from "jsonwebtoken";

const ACCESS_SECRET = process.env.JWT_ACCESS_SECRET; // long random string

export function signAccessToken(user) {
  return jwt.sign(
    { sub: String(user.id), role: user.role },
    ACCESS_SECRET,
    { algorithm: "HS256", expiresIn: "15m" }
  );
}

export function verifyAccessToken(token) {
  // Pin the algorithm list - never let the token's header choose it
  return jwt.verify(token, ACCESS_SECRET, { algorithms: ["HS256"] });
}
```

Passing `algorithms` explicitly matters. Historic JWT attacks abused
libraries that trusted the token's own `alg` header — for example accepting
`"none"` or confusing an RSA public key with an HMAC secret. `verify` also
checks `exp` and throws `TokenExpiredError` when the token is too old.

## An auth middleware

Clients send the access token in the `Authorization` header using the
Bearer scheme.

```js
export function requireAuth(req, res, next) {
  const header = req.get("authorization") ?? "";
  const [scheme, token] = header.split(" ");
  if (scheme !== "Bearer" || !token) {
    return res.status(401).json({ error: "Missing token" });
  }
  try {
    const claims = verifyAccessToken(token);
    req.user = { id: Number(claims.sub), role: claims.role };
    next();
  } catch {
    res.status(401).json({ error: "Invalid or expired token" });
  }
}

export const requireRole = (...roles) => (req, res, next) => {
  if (!roles.includes(req.user.role)) {
    return res.status(403).json({ error: "Forbidden" });
  }
  next();
};

app.get("/me", requireAuth, (req, res) => res.json(req.user));
app.delete("/users/:id", requireAuth, requireRole("admin"), deleteUser);
// No token        -> 401 { "error": "Missing token" }
// Token, not admin -> 403 { "error": "Forbidden" }
```

Remember the difference: **401** means "we don't know who you are",
**403** means "we know who you are, and you're not allowed".

## Access tokens vs refresh tokens

A JWT cannot easily be revoked before it expires — the server has no record
to delete. The standard answer is two tokens:

- **Access token** — short-lived (5 to 15 minutes), sent on every API call.
  If stolen, the damage window is small.
- **Refresh token** — long-lived (days), used only at `/auth/refresh` to get
  a new access token. Store it server-side (or a hash of it) so you can
  revoke it on logout or password change, and **rotate** it: issue a new
  refresh token on each use and invalidate the old one.

```js
app.post("/auth/refresh", async (req, res) => {
  const token = req.cookies.refreshToken;
  const stored = token && (await findValidRefreshToken(token)); // DB lookup by hash
  if (!stored) return res.status(401).json({ error: "Please log in again" });

  await revokeRefreshToken(stored.id);                 // rotation
  const user = await prisma.user.findUnique({ where: { id: stored.userId } });
  setRefreshCookie(res, await issueRefreshToken(user)); // new refresh token
  res.json({ accessToken: signAccessToken(user) });
});
```

## Where should the browser store tokens?

- **`localStorage`** — easy, but any XSS bug can read and exfiltrate the
  token.
- **httpOnly cookie** — invisible to JavaScript, so XSS cannot steal it, but
  the browser sends it automatically, so you must think about CSRF
  (`sameSite`, origin checks — covered in the next lesson).

A common, defensible setup: refresh token in an `httpOnly`, `secure`,
`sameSite` cookie scoped to the refresh path, and the access token held in
memory by the front end. Mobile apps use the platform's secure storage
instead.

## Sessions or JWTs?

For a classic web app on one domain, server sessions are simpler and
revocable. JWTs shine when many services need to verify identity without a
shared session store. Either way the password still gets hashed with bcrypt
or argon2 at login — tokens only replace what happens after it.

### Try it yourself

Add `/auth/login`, `/auth/refresh` and `/auth/logout` to an API. Set the
access token expiry to 30 seconds, call a protected route until you get a
401, then refresh and retry. Finally, paste a token into a base64 decoder and
confirm you can read the payload without the secret.
