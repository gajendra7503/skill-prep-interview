Error handling is one of the most common Express interview topics, and it
is also where Express 5 changed the most for everyday code. The goal is
simple: route handlers throw, one central middleware decides what the
client sees, and nothing internal (stack traces, SQL) ever leaks.

## Error middleware has four arguments

Express recognises error-handling middleware purely by its **arity**: a
function with exactly four parameters `(err, req, res, next)`. It is skipped
during normal requests and only runs after an error.

```js
// src/middleware/error-handler.js
export function errorHandler(err, req, res, next) {
  console.error(err);
  res.status(500).json({ error: { code: "INTERNAL", message: "Something went wrong" } });
}
```

Even if you never call `next`, keep the fourth parameter: with only three,
Express treats the function as ordinary middleware and it will never
receive errors. Register error middleware **last**, after all routes.

## Express 5 forwards async errors automatically

In Express 4, a rejected promise in an `async` handler was not caught; the
request hung and Node logged an unhandled rejection. People wrapped every
handler or installed `express-async-errors`. In Express 5, if a handler or
middleware returns a promise that rejects, the router calls `next(err)` for
you:

```js
// Express 5: no try/catch, no wrapper package needed
router.get("/:id", async (req, res) => {
  const expense = await expenses.findById(req.params.id); // if this rejects...
  res.json(expense);                                       // ...errorHandler receives the error
});
```

Two cases still need care:

- **Callbacks and timers** are not promises. An error thrown inside
  `setTimeout` or an old callback API is not caught; pass it to `next(err)`
  yourself or promisify the API.
- **Synchronous throws** were always caught, in Express 4 and 5.

## A custom HttpError

Throwing a plain `Error` gives the handler no idea which status to use.
A small subclass carries the status and a stable error code:

```js
// src/errors.js
export class HttpError extends Error {
  constructor(status, code, message, details) {
    super(message);
    this.name = "HttpError";
    this.status = status;
    this.code = code;
    this.details = details;
  }
}

export const notFound = (what) => new HttpError(404, "NOT_FOUND", `${what} not found`);
```

```js
router.get("/:id", async (req, res) => {
  const expense = await expenses.findById(Number(req.params.id));
  if (!expense) throw notFound("Expense");   // becomes a 404 response
  if (expense.userId !== req.user.id) throw new HttpError(403, "FORBIDDEN", "Not your expense");
  res.json(expense);
});
```

## The central error handler

```js
// src/middleware/error-handler.js
import { HttpError } from "../errors.js";

export function errorHandler(err, req, res, next) {
  if (res.headersSent) return next(err); // let Express close the connection

  if (err instanceof HttpError) {
    return res.status(err.status).json({
      error: { code: err.code, message: err.message, details: err.details },
    });
  }

  // Errors from express.json(): malformed JSON or body too large
  if (err.type === "entity.parse.failed") {
    return res.status(400).json({ error: { code: "INVALID_JSON", message: "Body is not valid JSON" } });
  }
  if (err.type === "entity.too.large") {
    return res.status(413).json({ error: { code: "PAYLOAD_TOO_LARGE", message: "Body is too large" } });
  }

  // Anything else is a bug or an outage: log everything, reveal nothing
  console.error({ err, method: req.method, url: req.originalUrl });
  res.status(500).json({ error: { code: "INTERNAL", message: "Something went wrong" } });
}
```

```bash
curl localhost:3000/api/v1/expenses/999
# 404 {"error":{"code":"NOT_FOUND","message":"Expense not found"}}

curl -X POST localhost:3000/api/v1/expenses -H "Content-Type: application/json" -d '{bad json'
# 400 {"error":{"code":"INVALID_JSON","message":"Body is not valid JSON"}}
```

The `res.headersSent` check matters when an error happens mid-stream (for
example while streaming a CSV export): you cannot send a new status once
headers are out, so delegating to Express's default handler closes the
connection instead.

## The 404 handler

An unknown URL is not an error; no route matched, so the request falls off
the end of the stack. Add a normal middleware after your routes and before
the error handler:

```js
// src/app.js
import express from "express";
import { expensesRouter } from "./routes/expenses.js";
import { errorHandler } from "./middleware/error-handler.js";
import { HttpError } from "./errors.js";

export const app = express();
app.use(express.json({ limit: "100kb" }));
app.use("/api/v1/expenses", expensesRouter);

app.use((req, res, next) => {
  next(new HttpError(404, "ROUTE_NOT_FOUND", `No route for ${req.method} ${req.path}`));
});

app.use(errorHandler); // always last
```

## Never leak stack traces

Express's built-in default handler includes the stack trace in the HTML
response unless `NODE_ENV` is `production`. Always set
`NODE_ENV=production` when deploying, and better still, use your own handler
so the response shape never depends on configuration. Log the full error
(with a request id) on the server; send the client only a code and a safe
message. Raw database errors are a classic leak: they can reveal table
names and query structure.

## Operational vs programmer errors

- **Operational** errors are expected: invalid input, missing record, a
  timed-out downstream service. Map them to 4xx or 503 responses.
- **Programmer** errors are bugs: `undefined is not a function`. Return a
  generic 500, log loudly and fix the code.

Process-level failures outside a request (`uncaughtException`,
`unhandledRejection`) are not handled by Express at all; log them and let a
process manager restart the app.

### Try it yourself

Add a `ConflictError` that extends `HttpError` with status 409 and throw it
when someone creates an expense with an `invoiceNo` that already exists.
Make an async route reject on purpose (for example with
`await Promise.reject(new Error("db down"))`) and confirm the client gets your generic 500 JSON while
the full error appears only in the server log.
